## 1. Vai trò và mục tiêu

Bạn là kỹ sư phần mềm full-stack giàu kinh nghiệm về .NET và web front-end, đã làm nhiều phần mềm bán hàng – kho cho doanh nghiệp vừa và nhỏ ở Việt Nam.

Nhiệm vụ: xây dựng mới hệ thống web "Quản lý Kho – Bán hàng" thay thế hoàn toàn phần mềm WinForms cũ (.NET Framework 2.0 + SQL Server). **Phần mềm cũ sẽ ngừng sử dụng**, không cần tương thích ngược với nó. Hệ thống gồm:

1. **Backend API** — ASP.NET Core.
2. **Web quản trị cho nhân viên** (Admin) — bán hàng, mua hàng, kho, thu chi, báo cáo, quản trị.
3. **Web đặt hàng cho khách hàng** (Customer Portal) — khách đăng ký bằng số điện thoại, tra cứu sản phẩm và gửi đơn đặt hàng.

Ưu tiên số 1 của giai đoạn đầu: **màn hình nhập hóa đơn bán hàng nhanh, chính xác, có gợi ý sản phẩm/khách hàng theo mã hoặc tên**.

### 2.1. Tóm tắt các bảng (đọc từ `cautrucdl.sql`)

**Danh mục**
- `sle_SAN_PHAM` — sản phẩm: `MA_SAN_PHAM`, `MA_VACH`, `TEN_SAN_PHAM`, nhóm, loại, ĐVT, ĐVT quy đổi + `TY_LE_QUY_DOI`, `GIA_NHAP`, `GIA_XUAT` (giá niêm yết/giá lẻ), `GIA_XUAT_SI` (giá sỉ), `HINH_ANH` (image), `LOAI_HINH_SP`, `TRANG_THAI`.
- `sle_NHOM_SAN_PHAM`, `sle_LOAI_SAN_PHAM`, `sle_DON_VI_TINH`, `sle_NHA_SAN_XUAT`, `sle_NHA_CUNG_CAP`.
- `sle_KHACH_HANG` — `MA_KHACH_HANG`, `TEN_KHACH_HANG`, địa chỉ, điện thoại, MST, `DISABLE`.
- `sle_KHO` — danh sách kho.

**Chứng từ hàng hóa**
- `sle_PHIEU_HANG` (header) — dùng chung cho mọi loại phiếu, phân biệt bằng `LOAI_PHIEU`: mua hàng, trả hàng NCC, bán lẻ, bán sỉ, khách trả hàng, nhập kho, xuất kho, chuyển kho (`ID_KHO_CHUYENDEN`), và (bổ sung) đơn đặt hàng online. Có tổng tiền, VAT, chiết khấu (`CHIETKHAU_THEOTIEN`), `HINH_THUC_TT`, `LOAI_THANH_TOAN`, `TRANG_THAI`, `LOI_NHUAN`, `DA_TRA_NO`.
- `sle_CHITIET_PHIEUHANG` (detail) — SP, ĐVT, số lượng, tỷ lệ quy đổi, giá vốn, đơn giá, % và tiền VAT, % và tiền chiết khấu, thành tiền, thứ tự.

**Kho**
- `sle_SANPHAM_KHO` — tồn hiện tại theo SP × kho + `SO_LUONG_CANH_BAO`.
- `sle_TON_KHO` (bình quân, có `GIA_TRUNG_BINH`), `sle_TON_KHO_FIFO` — dữ liệu tính giá vốn.
- `sle_PHIEU_KIEM_KE` + `sle_CHITIET_KIEMKE` — kiểm kê (SL sổ sách / thực tế / thừa / thiếu / phẩm chất 1-2-3), liên kết phiếu điều chỉnh nhập/xuất.

**Tiền**
- `sle_PHIEU_THUCHI` — phiếu thu/chi, có thể gắn `ID_PHIEU_HANG`, trả nợ nhiều phiếu (`ID_TRA_NO`, `PHIEU_TRA_NO` dạng chuỗi).

**Nhân sự & hệ thống**
- `hrm_NHAN_VIEN`, `hrm_HO_SO`, `hrm_CHUC_VU`.
- `sys_USERS`, `sys_MENU_FORM`, `sys_USERS_MENU` (quyền: xem/thêm/sửa/xóa/in/duyệt theo từng chức năng).
- `sys_ALL_TYPE` — bảng mã dùng chung (giá trị cho `LOAI_PHIEU`, `TRANG_THAI`, `HINH_THUC_TT`…).
- `sys_SETTING` — cấu hình (tên công ty, logo…), `sys_HISTORY` — nhật ký.

### 2.2. Quy ước nghiệp vụ lấy từ bản cũ
- Số phiếu: `<TIỀN TỐ><yyMM>_<số thứ tự 3 chữ số>`, ví dụ `BH201604_001`. Tiền tố: `BH` bán hàng, `MH` mua hàng, `CK` chuyển kho, `PT` phiếu thu, `PC` phiếu chi, `TH` trả hàng, `KK` kiểm kê, `DH` đơn đặt hàng online. Đánh số lại từ 001 mỗi tháng.
- Phiếu "Thanh toán ngay" tự sinh phiếu thu/chi tương ứng; "Chưa thanh toán" thì ghi công nợ.
- Mẫu in: Phiếu nhập kho mẫu S12-DN, Hóa đơn bán/mua hàng có số tiền bằng chữ, in tem mã vạch (tên, mã, barcode, giá).
- Phím tắt trên màn hình phiếu: F2 thêm SP, F8 xóa SP, F5 làm mới, Ctrl+S lưu, Ctrl+N tạo phiếu, F9 nhập bằng mã vạch, Esc đóng.

### 4.1. Triển khai bằng Docker — thư mục `deploy/`

Mọi service chạy trong container; máy chủ chỉ cần cài Docker Engine + Docker Compose plugin. Không đặt file Docker rải rác trong mã nguồn — tất cả nằm trong `deploy/`, chia theo vai trò:

```
deploy/
├─ docker/                       # Dockerfile của từng service (build context = thư mục gốc repo)
│  ├─ api/Dockerfile             # multi-stage: sdk:10.0 build → aspnet:10.0 runtime, chạy user non-root
│  ├─ admin/Dockerfile           # multi-stage: node build → nginx:alpine phục vụ file tĩnh
│  ├─ portal/Dockerfile          # như admin
│  └─ .dockerignore
├─ compose/
│  ├─ docker-compose.yml         # cấu hình chung cho mọi môi trường
│  ├─ docker-compose.dev.yml     # dev: mở cổng MySQL, Adminer, hot-reload
│  └─ docker-compose.prod.yml    # prod: chỉ mở 80/443 qua gateway, restart: always, giới hạn tài nguyên
├─ env/
│  ├─ .env.example               # mẫu biến môi trường (commit)
│  ├─ dev.env                    # không commit
│  └─ prod.env                   # không commit
├─ nginx/                        # gateway (reverse proxy)
│  ├─ nginx.conf
│  ├─ conf.d/
│  │  ├─ admin.conf              # admin.<domain>  → admin, /api → api
│  │  └─ portal.conf             # <domain>        → portal, /api → api, /hubs → SignalR (websocket)
│  └─ ssl/                       # chứng chỉ (không commit); hỗ trợ Let's Encrypt
├─ app/
│  ├─ admin.nginx.conf           # cấu hình nginx bên trong container admin (SPA fallback, cache, gzip)
│  └─ portal.nginx.conf
├─ mysql/
│  ├─ conf/my.cnf                # utf8mb4, time_zone +07:00, lower_case_table_names, innodb buffer
│  └─ init/                      # mount vào /docker-entrypoint-initdb.d — chạy database/00 → 01 → 02 khi DB trống
├─ scripts/                      # có cả bản .sh (Linux) và .ps1 (Windows)
│  ├─ build.sh / build.ps1       # build & gắn tag image theo version
│  ├─ up.sh / up.ps1             # khởi động theo môi trường: ./up.sh dev|prod
│  ├─ backup.sh / backup.ps1     # mysqldump nén .gz kèm ngày giờ
│  ├─ restore.sh / restore.ps1   # khôi phục từ file backup
│  └─ update.sh / update.ps1     # pull/build image mới, backup trước, rolling restart
├─ data/                         # dữ liệu bind-mount (không commit, có .gitkeep)
│  ├─ mysql/                     # dữ liệu MySQL
│  ├─ uploads/                   # ảnh sản phẩm
│  ├─ logs/                      # log Serilog của api, log nginx
│  └─ backups/                   # file backup MySQL
└─ README.md                     # hướng dẫn triển khai từng bước, cổng, biến môi trường, xử lý sự cố
```

**Các service trong `docker-compose.yml`**

| Service | Image | Ghi chú |
|---|---|---|
| `gateway` | nginx:alpine | Cổng duy nhất ra ngoài (80/443); định tuyến theo domain; nén gzip; giới hạn kích thước upload |
| `api` | build từ `deploy/docker/api` | Chỉ mạng nội bộ; healthcheck `/health`; mount `data/uploads`, `data/logs` |
| `admin` | build từ `deploy/docker/admin` | File tĩnh React; URL API cấu hình lúc chạy (file `config.js` sinh từ biến môi trường, không build lại image khi đổi domain) |
| `portal` | build từ `deploy/docker/portal` | Như admin |
| `mysql` | mysql:8.4 | Chỉ mạng nội bộ (prod không mở cổng); healthcheck `mysqladmin ping`; mount `data/mysql`, `mysql/conf`, `mysql/init` |
| `backup` | mysql:8.4 + cron | Backup hằng ngày 01:00, giữ 14 bản gần nhất trong `data/backups` |
| `adminer` | adminer | **Chỉ có ở dev** |

Yêu cầu:
- `api` chờ `mysql` healthy (`depends_on: condition: service_healthy`); `gateway` chờ `api`, `admin`, `portal`.
- Hai mạng Docker: `frontend-net` (gateway ↔ admin/portal/api) và `backend-net` (api ↔ mysql, backup); MySQL không nằm trong `frontend-net`.
- Mật khẩu, chuỗi kết nối, khóa JWT chỉ lấy từ `env/*.env`; không ghi cứng trong image hay compose.
- Image gắn tag theo version (`banhang-api:1.0.0`), không chỉ dùng `latest`.
- Log container giới hạn dung lượng (`max-size`, `max-file`).
- Lệnh chạy từ đầu trên máy mới: `cp env/.env.example env/prod.env` → sửa → `./scripts/up.sh prod`.

Nguyên tắc:
- Mọi phép ghi chứng từ (header + detail + cập nhật tồn + phiếu thu/chi) nằm trong **một transaction**.
- Tính tiền **luôn tính lại ở server**; client chỉ hiển thị tạm. Kiểu `decimal`, làm tròn tiền VND đến đồng.
- Các giá trị `LOAI_PHIEU`, `TRANG_THAI`, `HINH_THUC_TT`, `LOAI_THANH_TOAN`, `LOAI_HINH_SP` khai báo thành enum trong code **và** đồng bộ với `sys_ALL_TYPE`.
- API trả lỗi theo chuẩn ProblemDetails, thông báo tiếng Việt.

## 5. Yêu cầu chức năng — Web Admin (nhân viên)

### 5.1. ★ Hóa đơn bán hàng (ưu tiên cao nhất)

**Header**: Số phiếu (tự sinh, chỉ đọc), Ngày phiếu (mặc định hôm nay), Nhân viên bán (mặc định người đăng nhập), Kho xuất (mặc định kho của nhân viên), Khách hàng, Loại bán (lẻ/sỉ), Diễn giải, Thanh toán (Thanh toán ngay / Chưa thanh toán – ghi nợ), Hình thức TT (tiền mặt/chuyển khoản).

**Ô chọn khách hàng — gợi ý (autocomplete)**
- Gõ ≥ 1 ký tự → gọi API sau debounce 250 ms, tìm theo `MA_KHACH_HANG`, `TEN_KHACH_HANG`, `DIEN_THOAI`.
- Tìm **không phân biệt hoa/thường và không dấu** ("nguyen van" khớp "Nguyễn Văn").
- Dropdown hiển thị: Mã | Tên | Điện thoại | Địa chỉ (rút gọn). Thứ tự ưu tiên: khớp mã chính xác → khớp đầu chuỗi → khớp chứa.
- Có nút "+" thêm nhanh khách hàng mà không rời màn hình; có lựa chọn mặc định "Khách lẻ".
- Bỏ qua khách hàng `DISABLE = 1`.

**Lưới chi tiết — ô nhập sản phẩm gợi ý theo mã hoặc tên**
- Gõ vào ô sản phẩm → gợi ý theo `MA_SAN_PHAM`, `MA_VACH`, `TEN_SAN_PHAM` (không dấu, ưu tiên như trên), tối đa 20 kết quả.
- Mỗi dòng gợi ý: Mã | Tên | ĐVT | Giá bán (`GIA_XUAT` khi bán lẻ, `GIA_XUAT_SI` khi bán sỉ) | **Tồn tại kho đang chọn** (chỉ hiển thị ở Admin).
- Điều khiển hoàn toàn bằng bàn phím: ↑/↓ chọn, Enter xác nhận → con trỏ nhảy sang ô Số lượng → Enter → dòng mới, con trỏ về ô sản phẩm.
- Quét mã vạch (máy quét gửi chuỗi + Enter): khớp đúng `MA_VACH` thì thêm ngay; nếu SP đã có trong lưới thì cộng dồn số lượng.
- Chọn ĐVT: ĐVT chính hoặc ĐVT quy đổi; đổi ĐVT thì đổi đơn giá theo `TY_LE_QUY_DOI` và lưu `TY_LE_QUY_DOI` vào dòng chi tiết.
- Cột: STT, Mã, Tên, ĐVT, Số lượng, Đơn giá, % CK, Tiền CK, % VAT, Tiền VAT, Thành tiền, Ghi chú.
- Đơn giá mặc định lấy giá niêm yết; nhân viên được sửa nếu có quyền.
- Bán vượt tồn: **cảnh báo, không chặn** (cấu hình được trong `sys_SETTING`); chặn khi SL ≤ 0.
- Chỉ gợi ý SP đang kinh doanh (`TRANG_THAI`).

**Công thức** (mỗi dòng):
```
TienHang      = SoLuong × DonGia
TienChietKhau = TienHang × PT_CHIETKHAU / 100   (hoặc nhập trực tiếp tiền CK)
TienVat       = (TienHang − TienChietKhau) × PT_VAT / 100
ThanhTien     = TienHang − TienChietKhau + TienVat
GiaVon        = giá bình quân gia quyền tại thời điểm xuất
```
Footer: Tổng tiền hàng, Tổng chiết khấu (hỗ trợ chiết khấu cả phiếu theo % hoặc theo tiền — `CHIETKHAU_THEOTIEN`), Tổng VAT, **Tổng thanh toán**, Khách đưa / Tiền thừa (bán lẻ), Lợi nhuận (chỉ hiện với người có quyền).

**Khi lưu**
1. Validate; sinh số phiếu an toàn khi nhiều người lưu cùng lúc.
2. Ghi `sle_PHIEU_HANG` + `sle_CHITIET_PHIEUHANG`.
3. Trừ tồn `sle_SANPHAM_KHO` (quy đổi về ĐVT chính; cho phép âm nếu cấu hình cho phép), cập nhật giá vốn bình quân.
4. Tính `LOI_NHUAN = Σ(ThanhTien trước VAT − SoLuong quy đổi × GiaVon)`.
5. Nếu "Thanh toán ngay" → tạo `sle_PHIEU_THUCHI` (phiếu thu, `PT…`) gắn `ID_PHIEU_HANG`; nếu không → ghi nhận công nợ.
6. Ghi `sys_HISTORY`.

**Sau khi lưu**: In hóa đơn bán hàng **khổ A5** (mẫu mục 5.4; có nút "Lưu & In" để in ngay), In phiếu xuất kho, In phiếu thu; tạo phiếu mới bằng Ctrl+N. Đây là hóa đơn bán hàng nội bộ — **chưa tích hợp hóa đơn điện tử**.

**Sửa/Hủy**: sửa/hủy phiếu phải hoàn tồn kho và phiếu thu liên quan trong cùng transaction; hủy là đổi trạng thái (không xóa cứng); cần quyền `IS_EDIT`/`IS_DELETE`.

**Danh sách hóa đơn**: lọc theo ngày, khách hàng, nhân viên, kho, trạng thái thanh toán; tìm theo số phiếu; xem/sửa/in/xuất Excel.

### 5.2. Duyệt tài khoản khách hàng
- Danh sách tài khoản Portal đăng ký mới (trạng thái: Chờ duyệt → Đã duyệt / Từ chối / Khóa).
- Khi duyệt: nhân viên **liên kết với khách hàng có sẵn** trong `sle_KHACH_HANG` (gợi ý theo SĐT/tên) hoặc **tạo khách hàng mới** từ thông tin đăng ký (sinh `MA_KHACH_HANG` tự động).
- Từ chối phải nhập lý do; khóa/mở khóa tài khoản; đặt lại mật khẩu cho khách.
- Thông báo có tài khoản chờ duyệt (badge + SignalR).

### 5.3. Duyệt đơn đặt hàng online
- Danh sách đơn từ Portal (trạng thái: Chờ xác nhận → Đã xác nhận → Đang giao → Hoàn tất / Đã hủy).
- Hiển thị rõ dòng nào **đang thiếu hàng** so với tồn kho (vì khách được đặt cả khi hết hàng).
- Nhân viên xem, chỉnh số lượng/giá nếu cần, **chuyển thành hóa đơn bán hàng** (mở form 5.1 điền sẵn dữ liệu, có thể chuyển một phần nếu thiếu hàng) hoặc từ chối kèm lý do.
- In hóa đơn khổ A5 cho đơn online ở mọi trạng thái: khi chưa chuyển thì in **"Hóa đơn đặt hàng"** (số `DH…`); khi đã chuyển thì in **"Hóa đơn bán hàng"** (số `BH…`, có ghi kèm số đơn `DH…`).
- Thông báo có đơn mới (badge + âm thanh, SignalR).

### 5.4. Mẫu hóa đơn khổ A5 (dùng chung cho Admin và Portal)

**Mọi đơn hàng đều có hóa đơn**: dù khách tự đặt trên Portal hay nhân viên nhập cho khách ở Admin, hệ thống đều sinh hóa đơn xem/in được. Chỉ dùng **một mẫu A5** (148 × 210 mm, dọc), sinh PDF ở server bằng QuestPDF, để Admin và Portal in ra giống nhau.

- **Đầu trang**: logo, tên, địa chỉ, điện thoại, MST công ty (lấy từ `sys_SETTING`); tiêu đề "HÓA ĐƠN BÁN HÀNG" hoặc "HÓA ĐƠN ĐẶT HÀNG"; số phiếu, ngày, nhân viên bán (hoặc "Đặt online").
- **Khách hàng**: mã, tên, điện thoại, địa chỉ / địa chỉ giao hàng, MST (nếu có).
- **Bảng hàng**: STT, Tên hàng (kèm mã), ĐVT, SL, Đơn giá, CK, Thành tiền. Cột vừa khổ A5; tên dài thì tự xuống dòng; nhiều dòng thì sang trang và lặp lại tiêu đề bảng, có "Trang x/y".
- **Cuối bảng**: Tổng tiền hàng, Chiết khấu, VAT, **Tổng thanh toán**, Đã thanh toán, Còn nợ; số tiền bằng chữ; hình thức thanh toán; ghi chú.
- **Chân trang**: chữ ký Người mua / Người bán; dòng "Hóa đơn bán hàng nội bộ, không thay thế hóa đơn GTGT"; mã QR chứa số phiếu (tra cứu nhanh).
- Hóa đơn đã hủy in có dấu chìm "ĐÃ HỦY".
- Tùy chọn in: xem trước trong trình duyệt → In; tải PDF; in lại nhiều lần (ghi số lần in vào `sys_HISTORY`).
- API dùng chung: `GET /api/invoices/{id}/pdf?size=A5` (Admin) và `GET /api/portal/orders/{id}/pdf` (Portal, chỉ đơn của chính khách).

### 5.5. Các phân hệ khác (giai đoạn sau)
- **Danh mục**: sản phẩm (kèm import Excel, in tem mã vạch, ảnh SP, cờ "hiển thị trên Portal"), nhóm, loại, ĐVT, NSX, NCC, khách hàng, kho, nhân viên, chức vụ.
- **Mua bán hàng**: phiếu mua hàng, trả hàng NCC, bán sỉ, khách trả hàng — tái sử dụng component form phiếu của 5.1.
- **Kho**: nhập kho, xuất kho, chuyển kho, kiểm kê + tự sinh phiếu điều chỉnh thừa/thiếu.
- **Vốn bằng tiền**: phiếu thu, phiếu chi, trả nợ/thu nợ nhiều phiếu, tổng hợp thu chi, chi tiết công nợ.
- **Báo cáo**: nhập-xuất-tồn, sổ chi tiết hàng hóa, sổ chi tiết chứng từ, sổ chi tiết kho, doanh thu/lợi nhuận/công nợ theo đối tượng, biểu đồ; xuất Excel/PDF.
- **Bàn làm việc (dashboard)**: số phiếu theo loại, biểu đồ doanh thu, sản phẩm sắp hết hàng (`SO_LUONG < SO_LUONG_CANH_BAO`), số đơn online chờ xử lý, số tài khoản chờ duyệt.
- **Quản trị**: người dùng, phân quyền theo `sys_USERS_MENU` (Xem/Thêm/Sửa/Xóa/In/Duyệt), cấu hình công ty (`sys_SETTING`), nhật ký.

## 6. Yêu cầu chức năng — Web Khách hàng (Portal)

**Giao diện tương thích điện thoại và máy tính (responsive)**
- Một ứng dụng duy nhất, tự co giãn theo màn hình; không làm bản mobile riêng.
- Hỗ trợ từ 360px (điện thoại) đến ≥ 1920px (máy tính); kiểm thử ít nhất ở 3 cỡ: 375px (điện thoại), 768px (máy tính bảng), 1366px (máy tính).
- **Điện thoại**: thanh điều hướng dưới đáy (Trang chủ, Sản phẩm, Giỏ hàng, Đơn hàng, Tài khoản); sản phẩm 2 cột; bộ lọc mở dạng Drawer; nút "Thêm vào giỏ"/"Đặt hàng" cố định dưới màn hình; nút bấm ≥ 44px; ô nhập SĐT dùng bàn phím số (`inputMode="tel"`).
- **Máy tính**: menu ngang trên đầu + ô tìm kiếm lớn; bộ lọc cố định cột trái; sản phẩm 4–5 cột; giỏ hàng và tóm tắt đơn hiển thị song song.
- Bảng (đơn hàng, chi tiết đơn) trên điện thoại chuyển thành dạng thẻ (card), không cuộn ngang.
- Xem hóa đơn A5: máy tính xem trước PDF trong trang; điện thoại mở/tải PDF.
- Ảnh sản phẩm lazy-load, có kích thước thu nhỏ; trang đầu tải < 3 giây trên 4G.
- Chạy tốt trên Chrome, Safari (iOS), Edge, Firefox bản mới; có thể cài lên màn hình chính (PWA cơ bản: manifest + icon).

**Đăng ký & đăng nhập**
- Đăng ký bằng **số điện thoại** (bắt buộc, chuẩn hóa định dạng VN, không trùng) + họ tên + mật khẩu; tùy chọn email, địa chỉ, tên công ty/MST.
- Sau đăng ký, tài khoản ở trạng thái **Chờ duyệt**; khách chỉ đăng nhập và đặt hàng được sau khi **Admin xác nhận** (mục 5.2). Màn hình báo rõ "Tài khoản đang chờ cửa hàng xác nhận".
- Đăng nhập bằng SĐT + mật khẩu; quên mật khẩu: gửi yêu cầu, nhân viên đặt lại (chưa dùng SMS OTP ở giai đoạn này).
- Rate limit đăng nhập/đăng ký, captcha khi đăng ký.

**Danh mục sản phẩm**
- Tìm kiếm có gợi ý theo mã/tên (cùng API gợi ý với Admin nhưng chỉ trả trường công khai), lọc theo nhóm/loại, ảnh sản phẩm.
- **Giá hiển thị = giá niêm yết** (`GIA_XUAT`) — không hiển thị giá sỉ, giá nhập.
- **Không hiển thị tồn kho** dưới bất kỳ hình thức nào (kể cả "còn/hết hàng"); API Portal không được trả trường tồn kho.

**Giỏ hàng → Đặt hàng**
- **Cho phép đặt cả khi kho hết hàng.**
- Nhập địa chỉ giao (mặc định lấy từ hồ sơ), người nhận, SĐT nhận, ghi chú, phương thức thanh toán (COD / chuyển khoản).
- Server tính lại tổng tiền theo giá niêm yết tại thời điểm đặt; giá cuối cùng có thể được nhân viên điều chỉnh khi xác nhận.
- Lưu đơn: `sle_PHIEU_HANG` với `LOAI_PHIEU = Đơn đặt hàng`, `TRANG_THAI = Chờ xác nhận`, số phiếu `DH…` — **không trừ kho** cho tới khi nhân viên chuyển thành hóa đơn.

**Đơn hàng của tôi**
- Danh sách, trạng thái, chi tiết; hủy khi còn "Chờ xác nhận"; đặt lại đơn cũ.
- Ngay sau khi đặt và ở mỗi đơn đều có nút **Xem / In / Tải hóa đơn khổ A5** (mẫu mục 5.4): đơn chưa xác nhận in "Hóa đơn đặt hàng", đơn đã chuyển in "Hóa đơn bán hàng" theo giá đã chốt.
- Khách chỉ thấy đơn của chính mình (kiểm tra ở server).

**Hồ sơ**: sửa thông tin, sổ địa chỉ giao hàng, đổi mật khẩu.

## 7. Bổ sung CSDL (`database/01_bo_sung.sql`)

Nguyên tắc: **giữ nguyên các bảng/cột hiện có**, chỉ bổ sung những gì cần thiết, không làm sai khác lớn so với schema gốc. Vì phần mềm cũ đã bỏ, được phép chỉnh FK/index.

### 7.1. Chuyển schema từ SQL Server sang MySQL (`database/00_schema_mysql.sql`)

Giữ nguyên **tên bảng, tên cột (kể cả chữ hoa/thường), khóa chính**; chỉ đổi kiểu dữ liệu và cú pháp:

| SQL Server (gốc) | MySQL 8.4 |
|---|---|
| `USE [HLSALEDB]`, `[dbo].[...]`, `GO`, `ON [PRIMARY]`, `WITH (PAD_INDEX...)` | `CREATE DATABASE BTSALEDB CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci; USE BTSALEDB;` — bỏ các phần đặc thù T-SQL, dùng dấu `` ` `` |
| `nvarchar(n)` | `VARCHAR(n)` (utf8mb4) |
| `numeric(18,0)` dùng làm ID + `IDENTITY(1,1)` | `BIGINT AUTO_INCREMENT` (cột ID tham chiếu tới nó cũng là `BIGINT`) |
| `int IDENTITY(1,1)` | `INT AUTO_INCREMENT` |
| `numeric(18,3)` | `DECIMAL(18,3)` |
| `bit` | `TINYINT(1)` (EF ánh xạ `bool`) |
| `real` | `FLOAT` |
| `datetime` | `DATETIME(3)` |
| `image` | `LONGBLOB` |
| Bảng | `ENGINE=InnoDB` |
| Khóa ngoại | Tạo lại như gốc nhưng `ON DELETE RESTRICT` (xem mục 7.2 #5) |

Lưu ý MySQL:
- Tên bảng có chữ hoa: MySQL chạy trong container Linux nên phân biệt hoa thường → code luôn dùng đúng tên như schema; dev và prod đều dùng cùng container MySQL với `lower_case_table_names=0` trong `deploy/mysql/conf/my.cnf`.
- Collation `utf8mb4_0900_ai_ci` đã không phân biệt hoa/thường và dấu, nhưng **không coi "đ" = "d"** → vẫn cần cột `TEN_KHONG_DAU` do ứng dụng tính (mục 7.2 #8).
- Sinh số phiếu: bảng đếm `sys_SO_PHIEU(TIEN_TO, NAM_THANG, SO_CUOI)` + `SELECT ... FOR UPDATE` trong transaction.
- Múi giờ: lưu `DATETIME` theo giờ Việt Nam, đặt `time_zone = '+07:00'` cho kết nối.

## 8. Dữ liệu mẫu (`database/02_du_lieu_mau.sql`)

Script chạy lại được nhiều lần (idempotent):
- `sys_ALL_TYPE`: đủ mã cho loại phiếu (gồm Đơn đặt hàng), trạng thái phiếu, trạng thái đơn online, hình thức thanh toán.
- `sys_SETTING`: tên/địa chỉ công ty, cho phép bán âm kho = 1.
- `sys_MENU_FORM` theo cây menu ở mục 5; user `admin` (toàn quyền) + 2 nhân viên bán hàng + 1 thủ kho.
- 2 kho, 5 ĐVT (Cái, Hộp, Thùng, Kg, Chai), 5 nhóm, 8 loại, 3 NSX, 3 NCC.
- ~50 sản phẩm tiếng Việt có dấu (có SP có mã vạch, có SP quy đổi Thùng = 24 Chai, có SP tồn = 0), tồn kho ban đầu.
- ~20 khách hàng (có "Khách lẻ"); 5 tài khoản Portal: 3 đã duyệt, 2 chờ duyệt.
- Vài phiếu mua, bán, chuyển kho, thu chi, đơn online trong 2 tháng gần nhất để báo cáo có số liệu.

## 12. Quy ước đặt tên & thiết kế hướng đối tượng

Mục tiêu: người mới đọc code hiểu ngay; thêm loại chứng từ/danh mục mới chủ yếu bằng **thêm lớp kế thừa**, hạn chế sửa code cũ (nguyên lý Open/Closed). Tuân thủ SOLID.

### 12.1. Ngôn ngữ đặt tên

- **Code (C#, TypeScript, API) dùng tiếng Anh** theo thuật ngữ nghiệp vụ chuẩn; **CSDL giữ nguyên tên tiếng Việt** của schema gốc. Ánh xạ tên bảng/cột ↔ lớp/thuộc tính bằng EF Fluent Configuration (`IEntityTypeConfiguration<T>`), không để tên kiểu `SAN_PHAM` lọt vào Domain.
- Duy trì **bảng thuật ngữ** `docs/glossary.md` (CSDL ↔ Code ↔ Nhãn giao diện), cập nhật mỗi khi thêm khái niệm mới. Ví dụ:

| CSDL | Lớp / thuộc tính | Nhãn giao diện |
|---|---|---|
| `sle_SAN_PHAM` | `Product` | Sản phẩm |
| `MA_SAN_PHAM` / `MA_VACH` | `Product.Code` / `Product.Barcode` | Mã SP / Mã vạch |
| `GIA_XUAT` / `GIA_XUAT_SI` | `Product.RetailPrice` / `Product.WholesalePrice` | Giá niêm yết / Giá sỉ |
| `sle_KHACH_HANG` | `Customer` | Khách hàng |
| `sle_NHA_CUNG_CAP` | `Supplier` | Nhà cung cấp |
| `sle_KHO` / `sle_SANPHAM_KHO` | `Warehouse` / `StockBalance` | Kho / Tồn kho |
| `sle_DON_VI_TINH` | `Unit` | Đơn vị tính |
| `sle_PHIEU_HANG` | `Voucher` (lớp trừu tượng) | Phiếu / Chứng từ |
| `sle_CHITIET_PHIEUHANG` | `VoucherLine` | Dòng chi tiết |
| `LOAI_PHIEU` | `VoucherType` (enum) | Loại phiếu |
| `sle_PHIEU_THUCHI` | `CashVoucher` (trừu tượng) → `CashReceipt` / `CashPayment` | Phiếu thu / Phiếu chi |
| `sle_PHIEU_KIEM_KE` | `StockCount` / `StockCountLine` | Phiếu kiểm kê |
| `web_TAI_KHOAN_KH` | `CustomerAccount` | Tài khoản khách |

- Bảng/cột **mới** trong CSDL theo đúng quy ước gốc: tiền tố phân hệ (`sle_`, `sys_`, `hrm_`, `web_`) + `CHU_HOA_GACH_DUOI` tiếng Việt không dấu.

### 12.2. Quy tắc đặt tên

**C# (.NET)**
- `PascalCase`: lớp, interface, method, property, enum, hằng số. `camelCase`: biến cục bộ, tham số. `_camelCase`: field private.
- Interface tiền tố `I` (`IVoucherNumberGenerator`); method bất đồng bộ hậu tố `Async`.
- Hậu tố theo vai trò, thống nhất toàn dự án: `...Service`, `...Repository`, `...Controller`, `...Validator`, `...Configuration` (EF), `...Handler` (domain event), `...Strategy`, `...Document` (mẫu in PDF), `...Dto`, `...Request`, `...Response`, `...Query`.
- Boolean bắt đầu bằng `Is/Has/Can/Allow` (`IsDisabled`, `AllowNegativeStock`).
- Tiền dùng `decimal`, tên có `Amount`/`Price`/`Total` (`DiscountAmount`, `VatRate`, `GrandTotal`); số lượng dùng `Quantity`; tỷ lệ dùng `Rate`.
- Không viết tắt khó hiểu; chỉ cho phép `Id`, `Dto`, `Vat`, `Pdf`, `Url`.
- Một lớp public / một file; tên file = tên lớp.
- Tổ chức theo tính năng (feature folder): `Features/Sales/Invoices/`, `Features/Catalog/Products/`, `Features/Portal/Orders/`…

**TypeScript / React**
- Component `PascalCase` (`ProductAutocomplete.tsx`); hook `useCamelCase` (`useProductSearch.ts`); type/interface `PascalCase`, không tiền tố `I`; hằng số `UPPER_SNAKE_CASE`.
- Thư mục theo tính năng giống backend: `src/features/sales-invoices/`, `src/features/catalog/products/`.

**API REST**
- Danh từ số nhiều, `kebab-case`: `GET /api/sales-invoices`, `POST /api/sales-invoices/{id}/cancel`, `GET /api/products/suggest?q=`, `GET /api/portal/orders`.
- JSON `camelCase`; ngày giờ ISO 8601.

### 12.3. Thiết kế hướng đối tượng, thừa kế & mở rộng

**Lớp cơ sở chung (Domain)**
```
Entity<TId>                         // Id, so sánh bằng theo Id
 └─ AuditableEntity<TId>            // CreatedAt, CreatedBy, UpdatedAt, UpdatedBy, RowVersion
     └─ (các thực thể nghiệp vụ)
Interface đánh dấu: ISoftDeletable (IsDisabled), IHasCode (Code), IHasName (Name)
```

**Cây chứng từ hàng hóa — dùng chung bảng `sle_PHIEU_HANG` (EF Core TPH, discriminator = `LOAI_PHIEU`)**
```
Voucher (abstract)                  // Number, Date, Warehouse, Lines, Totals, Status
 │   + abstract VoucherType Type
 │   + abstract StockDirection Direction   // In / Out / Transfer / None
 │   + virtual  void Validate()
 │   + RecalculateTotals()                 // dùng chung cho mọi loại phiếu
 ├─ SalesVoucher (abstract)         // Customer, PaymentMode, Profit
 │   ├─ SalesInvoice                // Bán lẻ / bán sỉ          — Out
 │   ├─ SalesReturn                 // Khách trả hàng           — In
 │   └─ OnlineOrder                 // Đơn đặt hàng Portal       — None (không trừ kho)
 ├─ PurchaseVoucher (abstract)      // Supplier
 │   ├─ PurchaseReceipt             // Mua hàng                  — In
 │   └─ PurchaseReturn              // Trả hàng NCC              — Out
 └─ InventoryVoucher (abstract)
     ├─ StockReceipt                // Nhập kho khác             — In
     ├─ StockIssue                  // Xuất kho khác             — Out
     └─ StockTransfer               // Chuyển kho (+ DestinationWarehouse) — Transfer
```

**Dịch vụ theo mẫu Template Method**
```
VoucherService<TVoucher> (abstract) where TVoucher : Voucher
  public  async Task<TVoucher> PostAsync(request)       // quy trình cố định, KHÔNG override:
     1. MapAndValidate()        (virtual)
     2. AssignNumber()          → IVoucherNumberGenerator
     3. RecalculateTotals()
     4. ApplyStockEffect()      → IStockLedgerService theo Direction
     5. OnPosted()              (virtual hook: tạo phiếu thu/chi, tính lợi nhuận, thông báo…)
     6. Save trong 1 transaction + phát domain event VoucherPosted
  SalesInvoiceService : VoucherService<SalesInvoice>    // override OnPosted → tạo CashReceipt
  PurchaseReceiptService : VoucherService<PurchaseReceipt>
  ...
```
→ Thêm loại phiếu mới = thêm 1 lớp con `Voucher` + 1 lớp con `VoucherService` + đăng ký DI; không sửa quy trình chung.

**Strategy / interface để thay thế được**
- `ICostingStrategy` → `WeightedAverageCostingStrategy` (mặc định), `FifoCostingStrategy` (để sẵn chỗ mở rộng).
- `IPriceResolver` → `ListPriceResolver` (giá niêm yết), sau này `CustomerGroupPriceResolver`, `PromotionPriceResolver`.
- `IVoucherNumberGenerator` → `MonthlySequenceNumberGenerator` (`BH2611_001`).
- `ITextNormalizer` → `VietnameseTextNormalizer` (bỏ dấu, "đ" → "d") dùng cho tìm kiếm.
- `INotificationSender` → `SignalRNotificationSender`, sau này `SmsNotificationSender`, `ZaloNotificationSender`.

**Danh mục dùng lớp generic**
- `CatalogEntity` (abstract: `Code`, `Name`, `Description`, `IsDisabled`) cho ĐVT, nhóm, loại, NSX, kho….
- `CatalogService<TEntity, TDto>` và `CatalogController<TEntity, TDto>` cung cấp sẵn danh sách/tìm/thêm/sửa/xóa mềm/gợi ý; danh mục cụ thể chỉ kế thừa và override phần khác biệt.

**Mẫu in kế thừa**
- `PdfDocumentBase` (khổ giấy, header công ty, footer, đánh số trang) → `A5VoucherDocument` (abstract: bảng hàng, tổng tiền, tiền bằng chữ) → `SalesInvoiceDocument`, `OnlineOrderDocument`, `CashReceiptDocument`….

**Front-end hướng thành phần, mở rộng bằng cấu hình**
- `VoucherForm` dùng chung (header + lưới dòng + footer tổng tiền + phím tắt), nhận cấu hình theo loại phiếu (cột hiển thị, loại giá, có trừ kho không…); các màn hình phiếu chỉ truyền cấu hình và phần riêng.
- `CatalogPage<T>` generic cho các danh mục; `EntityAutocomplete<T>` dùng chung cho gợi ý sản phẩm, khách hàng, NCC.
- Logic gọi API tách ra hook (`useSalesInvoice`, `useProductSearch`); component chỉ hiển thị.

**Yêu cầu chất lượng**
- Không đặt nghiệp vụ trong Controller; Controller mỏng, chỉ nhận request → gọi service → trả response.
- Mỗi lớp nghiệp vụ có unit test; lớp cơ sở có test riêng để lớp con không phải test lại phần chung.
- Bật nullable reference types, `TreatWarningsAsErrors`; dùng `.editorconfig` + ESLint/Prettier để ép quy ước đặt tên tự động.

## 13. Ý tưởng chuyên sâu — yêu cầu AI chủ động bổ sung

Khi thực hiện, AI **không chỉ làm đúng yêu cầu mà phải chủ động suy nghĩ như một kiến trúc sư nghiệp vụ**: ở đầu mỗi giai đoạn, đưa ra danh sách ý tưởng bổ sung cho giai đoạn đó, mỗi ý tưởng gồm: vấn đề giải quyết, lợi ích, chi phí/độ phức tạp, ảnh hưởng tới schema. **Chỉ triển khai sau khi chủ dự án duyệt**; ý tưởng chưa duyệt ghi vào `docs/ideas-backlog.md`.

**Nhóm A — đưa luôn vào phạm vi (chi phí thấp, giá trị cao)**
1. **Chống gửi trùng (idempotency key)**: mỗi lần lưu hóa đơn/đặt hàng kèm khóa duy nhất từ client; mạng chập chờn bấm 2 lần không sinh 2 hóa đơn.
2. **Sổ kho (stock ledger)** — bảng `sle_SO_KHO` ghi mỗi biến động tồn (phiếu, SP, kho, SL vào/ra, giá vốn, tồn sau); tồn kho và sổ chi tiết hàng hóa truy ra được từng dòng, dễ đối soát.
3. **Nhiều hóa đơn mở cùng lúc** ở màn hình bán hàng (dạng tab) + tự lưu nháp, khi đang bán cho khách này có thể tạm dừng phục vụ khách khác.
4. **Nhớ giá bán gần nhất cho từng khách** và gợi ý sản phẩm khách hay mua lên đầu danh sách gợi ý.

**Nhóm B — đề xuất, chờ duyệt**
5. **Khóa sổ theo kỳ**: không cho sửa/hủy chứng từ thuộc tháng đã khóa.
6. **Hạn mức công nợ khách hàng**: cảnh báo/chặn khi bán ghi nợ vượt hạn mức.
7. **Lịch sử thay đổi giá** sản phẩm (ai đổi, lúc nào, giá cũ/mới).
8. **Nhật ký chi tiết dạng so sánh trước/sau** (JSON diff) cho chứng từ và danh mục quan trọng.
9. **Import Excel có bước xem trước và báo lỗi từng dòng** trước khi ghi.
10. **Mã QR chuyển khoản động** (VietQR theo số tiền + nội dung = số hóa đơn) in trên hóa đơn A5 và hiện ở Portal.
11. **Giám sát hệ thống**: health dashboard, OpenTelemetry, cảnh báo khi backup thất bại.
12. **Outbox pattern** cho thông báo/sự kiện để không mất thông báo khi lỗi giữa chừng.

---

**Lệnh cho AI khi thực thi prompt này:** đọc toàn bộ tài liệu ở mục 2, các quyết định ở mục 11, quy ước code ở mục 12 và yêu cầu ý tưởng ở mục 13, sau đó bắt đầu từ Giai đoạn 0. Đầu mỗi giai đoạn trình bày ý tưởng bổ sung (mục 13) và chờ duyệt. Không tự ý mở rộng phạm vi ngoài giai đoạn đang làm; khi gặp mâu thuẫn giữa schema và nghiệp vụ thì dừng lại hỏi.
